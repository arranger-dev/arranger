Arranger: validation report (2026-09-23, updated 2026-09-24)
========================================

What was run
  - go build, go vet and go test ./... (all packages pass).
  - A live server on a scratch data dir, driven over its HTTP API and SSE stream, with fake
    agents (the "generic" runtime running shell scripts): a single worker, a manager with two
    workers (plan, parallel run, review, merge, checks), stop, double run, merge preview/merge,
    bad inputs, CSRF, restart during a run, and shutdown during a run.
  - The UI script was syntax-checked and its changes reviewed by reading the code. It was NOT
    clicked through in a browser (no browser automation in this session). See "Not verified".


Found and fixed
---------------
1. Saving a project on a freshly `git init`-ed repo (no commits, base branch blank) failed with
   git's raw "ambiguous argument 'HEAD'" error.
   Now: "<repo> has no commits yet. Make a first commit (e.g. git commit --allow-empty -m
   "initial commit") and save again". An orphan branch with a blank base also gets a clear message.
   (internal/git/git.go CheckRepo, tests in git_test.go and server_test.go)

2. "Click Run, nothing happens." The server rejects a goal without checks ("needs at least one
   check"), but the UI only showed that in the small header message, which is easy to miss.
   Saving the goal (with checks) and running again then worked, which looked like "Save goal
   starts the agent".
   Now: Run checks for a title and checks first, focuses the missing field, and shows every
   outcome (starting, error) in a status line at the top of the inspector. Run always saves the
   goal form first.

3. Working animations appeared late. A run only published a status after its git worktree was
   created, and the page waited for a summary refetch before it changed the box.
   Now: Run and a manager's hand-off to each report publish a "starting" status immediately, the
   page applies live status changes to the box directly, and links animate both ways: down while a
   manager plans or hands work to a report, up while a report works, and up again while the manager
   reviews what came back.

4. Removing a running agent from the canvas and saving was accepted. The agent's process kept
   running with no box to stop it from, and stopping it later recreated a goal row for a deleted
   agent.
   Now: the save is refused with 409 ("<name> is running; stop it before removing it"), and the ×
   on a running box explains that instead of removing it.

5. Running an agent that isn't saved returned "agent x: sql: no rows in result set".
   Now: "agent x not found; save the arrangement first".

6. Stopping the server (Ctrl-C / SIGTERM) left agent processes running on their own. The next
   start marked them "stopped" while they were still editing the worktree.
   Now: the server stops all runs (up to 10s) before it exits. A SIGKILL still orphans them (see
   open item 2).


Fixed in v5 (2026-09-24)
------------------------
7. "Promote to Lead didn't work." Promote failed with a raw `git apply` error whenever the
   manager already had the change, which is the normal state after a team run (the manager merged
   the report's work). It also failed when the manager's files had moved on since. And even when
   it worked, the report's own diff looked unchanged, because promote copies rather than moves.
   Now: hunks the manager already has are skipped and reported ("Lead already has this change").
   The rest apply directly, or as a 3-way merge when the manager's files have moved on. A real
   conflict names the files and leaves the manager's work untouched. The message says how many
   changes were copied and that they stay in the report's diff too.
   (git.ApplyHunks, TestPromoteToManager)

8. Agents didn't pick up new commits on their branch. A worktree was created once and reused, so
   commits made to main (or to a manager's branch) afterwards never reached the agent.
   Now: every run first merges the latest commits of the branch the agent works from, and logs
   "synced with main: N new commit(s)". The Diff tab shows "main has N new commits" with a Sync
   button to do it on demand. The diff is re-measured from the new tip, so upstream changes never
   show as the agent's work. A conflicting sync is abandoned. The run goes ahead from where the
   agent left off, with a warning in the log. (git.Sync, Orchestrator.Sync, TestSync,
   TestSyncWithBaseBranch)

9. Save goal gave no feedback where you clicked. It now shows "Saved at <time>" under the button,
   warns when the goal has no checks yet, and clears once you edit again.


Still open (not fixed)
----------------------
1. `go install github.com/arranger-dev/arranger/cmd/arranger@latest` can't work: go.mod declares
   the module as plain `arranger`. Fixing it means renaming the module path to
   github.com/arranger-dev/arranger and updating every import. The README only documents the
   install script and building from a clone until then.

2. Stopping an agent kills the agent CLI process only, not processes it started (shells, test
   runners, dev servers). The same applies after a SIGKILL of the server. Fix: start agents in their
   own process group and kill the group (the code already has a "ponytail" note for this).

3. New files an agent creates don't show in the Diff tab until the next checkpoint commit (after
   the attempt ends), because `git diff` doesn't include untracked files.

4. If any report fails, its manager goes to "blocked" and waits for you. It doesn't re-plan
   around the failure.

5. Performance: while an agent is selected, every summary refresh also refetches that agent's goal.
   With busy agents sending usage updates, that's up to about 6 extra requests per second. It's
   harmless locally, but it could be pushed over SSE instead.

6. /arrange?p=<unknown id> silently shows the first project instead of saying the project doesn't
   exist.

7. A slow browser tab drops live events when its 256-message buffer is full. Logs refetch when the
   tab is opened, but a missed status only corrects itself on the next status change.

8. Checks run with `sh -c`, so on Windows they need Git Bash (or another sh) on PATH.

9. A generic-runtime command is split on spaces, so quoting doesn't work
   (sh -c 'echo x > f' breaks). Put the command in a script and run `sh script.sh`.
